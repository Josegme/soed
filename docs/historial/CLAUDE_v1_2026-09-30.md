# SOED — Instrucciones para Claude Code

Plataforma web para organizaciones de eventos de danza: temporadas con selectivos y final, inscripciones, música, orden de salida en vivo, puntajes de jurado, acreditación, clases y entradas. Español y portugués. Una instancia aislada por cliente.

## Fuentes de verdad (leer antes de trabajar)

1. `docs/PLAN_DESARROLLO.md` — plan vigente. Si un documento lo contradice, gana el plan.
2. `architecture/decisions/` — ADR-0001 a ADR-0005. No contradecirlos; si algo cambia, se crea un ADR nuevo.
3. `docs/GLOSARIO.md` — vocabulario único. Usar exactamente esos términos en código, UI y commits.
4. `specs/` — cada funcionalidad tiene su spec. **No se implementa nada sin spec aprobado.**
5. `architecture/ARQUITECTURA.md` y `architecture/DATABASE_SCHEMA.md` — capas y modelo de datos.

## Stack

Next.js 15 (App Router, Server Actions, Route Handlers) + TypeScript estricto en Vercel · Supabase (Postgres, Auth, Storage, Realtime, pgmq, pg_cron, Edge Functions) · Zod · next-intl (`es`, `pt-BR`) · Resend + React Email · Tailwind + shadcn/ui · Vitest + Playwright · pnpm + Turborepo · GitHub Actions.

No usar NestJS, Prisma, Redis, Socket.io, BullMQ ni S3. Están descartados (ADR-0002).

## Estructura

```
apps/web/src/{app,modules,lib}     UI, casos de uso, adaptadores
packages/{domain,shared-types,ui,email-templates}
supabase/{migrations,functions,tests,seed.sql}
clients/<slug>/{client.config.ts,theme.css,assets,seed.sql}
specs/  docs/  architecture/  .claude/commands/
```

## Reglas de arquitectura (no negociables)

- **Clean Architecture:** `domain` no importa nada externo. `application` define casos de uso e interfaces. `infrastructure` implementa con Supabase/Resend. `interface` (server actions, route handlers, componentes) solo llama casos de uso.
- **Result Pattern:** los casos de uso devuelven `Result<T, E>`; no lanzan excepciones por errores de negocio.
- **Single-tenant:** ninguna tabla lleva `tenant_id`. Prohibido `if (cliente === 'x')`: si falta variación, se agrega un parámetro en `client.config.ts` y se registra un ADR (ADR-0003).
- **Eventos independientes:** toda tabla con datos de evento lleva `evento_id` indexado y RLS por evento (ADR-0004). Roles por evento en `evento_miembro`.
- **El pago nunca limita la participación.** La plataforma calcula la liquidación y el organizador registra cobros a mano. No hay estados ni validaciones que bloqueen inscripción, acreditación o presentación por deuda.
- **Pases a la final son manuales.** No implementar reglas automáticas de clasificación.
- **Reglamento configurable:** categorías, tolerancias, tiempos, géneros y umbrales viven en `ReglamentoEvento`, no en constantes. El preset 2026 está en `clients/_template/seed.sql`.
- **i18n:** ningún texto visible en literal; todo es clave de `messages/{es,pt}/`. Contenido del organizador en `jsonb {es, pt}`. CI falla si falta una clave (ADR-0005).
- **Seguridad:** toda tabla nueva con RLS en la misma migración; la `service_role` solo en servidor; sin secretos en el repo; archivos en buckets privados con URLs firmadas; entradas validadas con Zod en el borde.
- **Base de datos:** migraciones SQL a mano, aditivas e idempotentes en lo posible; índice en toda clave foránea; políticas con `(select auth.uid())`; funciones auxiliares en el esquema `private`. Nunca editar el esquema desde el panel de Supabase.

## Flujo de trabajo por spec

1. Rama `feat/<id-spec>-<tema>` desde `main`.
2. `/spec <id>`: leer el spec, listar supuestos y preguntas, proponer plan. **Sin código hasta aprobación.**
3. Implementar por capas, en este orden: migración + RLS + pruebas de RLS → dominio (con tests) → casos de uso → interfaz → UI (es y pt).
4. Correr `pnpm lint && pnpm typecheck && pnpm test` y las pruebas de RLS antes de cada commit.
5. `/review`: revisión propia contra el spec y esta lista de reglas.
6. PR con checklist del spec; preview de Vercel contra el Supabase de staging.

## Comandos

```
pnpm dev                  # desarrollo
pnpm lint | typecheck | test | test:e2e
pnpm i18n:check           # claves es/pt completas
pnpm db:start | db:reset  # Supabase local
pnpm db:test              # pruebas SQL de RLS y reglas de datos
pnpm db:types             # tipos TypeScript desde el esquema
```

## Permisos y límites

- **Sin preguntar:** leer, editar archivos, tests, lint, typecheck, Supabase local, migraciones locales, crear ramas y commits.
- **Pedir aprobación:** `git push`, abrir o fusionar PR, aplicar migraciones a staging o producción, cambiar variables de entorno o DNS, instalar dependencias nuevas, borrar datos.
- **Nunca:** actuar sobre producción sin aprobación explícita, imprimir o commitear secretos, desactivar RLS, usar `--no-verify`.
- Secretos solo en Vercel y `.env.local`. Ver `.env.example`.

## Commits y PRs

Conventional Commits en español o inglés (`feat(inscripciones): ...`). Un PR por spec o subtarea. Cada PR enlaza su spec y marca la Definition of Done.

## Cuando falte información

No inventar reglas de negocio. Marcar el supuesto, dejarlo como pregunta en el spec y seguir con lo que no depende de él.
